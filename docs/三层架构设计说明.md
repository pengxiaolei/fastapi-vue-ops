# 后端三层架构设计说明

## 架构概述

本项目采用经典的三层架构设计，将代码按照职责划分为三个层次：

```
┌─────────────────────────────────────────┐
│         API 层 (接口层)                  │
│    - 路由定义                            │
│    - 参数接收与校验                    │
│    - 响应格式化                          │
├─────────────────────────────────────────┤
│         Logic 层 (业务逻辑层)          │
│    - 核心业务逻辑处理                    │
│    - 数据组装与转换                      │
│    - 业务规则校验                        │
├─────────────────────────────────────────┤
│         Service 层 (数据访问层)        │
│    - 数据库 CRUD 操作                   │
│    - 与 ORM 模型交互                    │
├─────────────────────────────────────────┤
│         Model 层 (数据模型层)          │
│    - 数据库表结构定义                    │
│    - SQLAlchemy 模型                   │
└─────────────────────────────────────────┘
```

---

## 各层职责说明

### 1. API 层 (`app/api/`)

**职责**：负责处理 HTTP 请求，只做路由转发和参数处理

**文件结构**：
```
app/api/v1/
├── machines.py    # 机器管理接口
├── tags.py        # 标签管理接口
└── groups.py      # 分组管理接口
```

**代码原则**：
- ✅ 只定义路由和请求方式
- ✅ 只做参数接收和基础校验
- ✅ 调用 Logic 层获取结果
- ✅ 统一包装响应格式
- ❌ 不包含业务逻辑
- ❌ 不直接操作数据库
- ❌ 不做复杂的数据处理

**示例代码**：
```python
@router.post("/list", response_model=ApiResponse[MachineListResponse])
async def get_machine_list(params: dict = {}, db: Session = Depends(get_db)):
    """获取机器列表"""
    # 调用 Logic 层处理业务
    result = MachineLogic.get_machine_list(
        db,
        page=params.get("page", 1),
        page_size=params.get("page_size", 20),
        keyword=params.get("keyword"),
    )
    # 统一返回格式
    return ApiResponse.ok(data=result, action="machine.list")
```

---

### 2. Logic 层 (`app/logic/`)

**职责**：负责核心业务逻辑处理，是整个系统的业务大脑

**文件结构**：
```
app/logic/
├── __init__.py       # 模块导出
├── machine_logic.py   # 机器管理业务逻辑
├── tag_logic.py       # 标签管理业务逻辑
└── group_logic.py     # 分组管理业务逻辑
```

**代码原则**：
- ✅ 处理核心业务逻辑
- ✅ 数据组装和格式转换
- ✅ 业务规则校验
- ✅ 调用 Service 层获取数据
- ✅ 多个 Service 的组合调用
- ❌ 不直接接收 HTTP 请求
- ❌ 不直接操作 ORM

**示例代码**：
```python
class MachineLogic:
    @staticmethod
    def get_machine_list(
        db: Session,
        page: int = 1,
        page_size: int = 20,
        keyword: Optional[str] = None,
    ) -> MachineListResponse:
        """获取机器列表业务逻辑"""
        # 调用 Service 层获取数据
        skip = (page - 1) * page_size
        machines, total = MachineService.get_machines(
            db, skip=skip, limit=page_size, keyword=keyword
        )

        # 组装响应数据
        return MachineListResponse(
            total=total,
            page=page,
            page_size=page_size,
            total_pages=(total + page_size - 1) // page_size,
            data=machines
        )
```

---

### 3. Service 层 (`app/services/`)

**职责**：负责数据访问和数据库操作，封装 CRUD

**文件结构**：
```
app/services/
├── __init__.py            # 模块导出
├── machine_service.py     # 机器数据操作
├── tag_service.py         # 标签数据操作
└── group_service.py       # 分组数据操作
```

**代码原则**：
- ✅ 封装数据库 CRUD 操作
- ✅ 与 SQLAlchemy ORM 交互
- ✅ 提供原子化的数据操作方法
- ✅ 单一职责，一个 Service 只操作一个主模型
- ❌ 不包含业务逻辑
- ❌ 不组合多个模型操作

**示例代码**：
```python
class MachineService:
    @staticmethod
    def get_machine(db: Session, machine_id: int) -> Optional[Machine]:
        """根据ID获取机器"""
        return db.query(Machine).filter(
            and_(Machine.id == machine_id, Machine.is_deleted == False)
        ).first()

    @staticmethod
    def create_machine(db: Session, machine_in: MachineCreate) -> Machine:
        """创建机器"""
        machine = Machine(**machine_in.model_dump())
        db.add(machine)
        db.commit()
        db.refresh(machine)
        return machine
```

### 4. Model 层 (`app/models/`)

**职责**：定义数据库表结构和数据模型

**文件结构**：
```
app/models/
├── __init__.py      # 模块导出
├── base.py          # 基础模型混入类
└── machine.py       # 机器、标签、分组模型
```

**代码原则**：
- ✅ 只定义表结构和字段
- ✅ 定义模型间关联关系
- ✅ 使用 SQLAlchemy 声明式语法
- ❌ 不包含业务逻辑
- ❌ 不做数据校验

## 调用关系

```
HTTP 请求
    ↓
API 层 (machines.py)
    ↓ 调用
Logic 层 (machine_logic.py)
    ↓ 调用
Service 层 (machine_service.py)
    ↓ 操作
Model 层 + 数据库
    ↓ 返回
逐层返回结果
```

---

## 架构优势

### 1. 关注点分离
- 每个层次职责单一，代码清晰
- 修改某一层不会影响其他层
- 便于定位和修复问题

### 2. 代码复用
- Logic 层可以被多个 API 复用
- Service 层可以被多个 Logic 复用
- 避免重复代码

### 3. 便于测试
- 各层可以独立进行单元测试
- Logic 层的业务逻辑测试不需要启动 HTTP 服务
- Service 层可以单独测试数据库操作

### 4. 易于维护
- 新增功能时结构清晰
- 代码结构统一，团队协作成本低
- 便于进行代码审查

### 5. 扩展性强
- 新增接口：只需要在 API 层添加路由，调用现有 Logic
- 新增业务：只需要在 Logic 层添加方法，组合现有 Service
- 新增数据操作：只需要在 Service 层添加方法
